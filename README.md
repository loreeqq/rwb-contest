# RWB Contest — сервис трендов поисковых запросов

Тестовое задание для позиции Backend-разработчика на Go.

Сервис принимает поток поисковых запросов из RabbitMQ, хранит статистику за последние 5 минут и отдает самые популярные запросы через HTTP API.

Ссылка на github-репозиторий: https://github.com/loreeqq/rwb-contest.

---

## Что реализовано

В проекте реализованы основные требования задания:

- чтение поисковых событий из брокера сообщений;
- расчет Top-N запросов за последние 5 минут;
- HTTP API для получения топа;
- динамический стоп-лист без перезапуска сервиса;
- защита от аномальных всплесков одинаковых запросов;
- быстрый локальный запуск через Docker Compose.

Дополнительно добавлены:

- пул воркеров сообщений;
- корректное завершение приложения;
- повторные попытки подключения к RabbitMQ;
- базовые метрики в формате Prometheus;
- нагрузочное тестирование;
- unit-тесты ключевой бизнес-логики;
- отчет покрытия тестами через `make gcov_report`.

## Архитектурная идея

По условию задачи ручка получения топа должна работать очень быстро, а запросов на чтение ожидается намного больше, чем входящих событий.

Поэтому основной упор сделан на быстрое чтение:

- данные хранятся в памяти;
- используется фиксированное окно в 300 секунд;
- старые данные не удаляются отдельным процессом, а перезаписываются в кольцевом буфере;
- чтение защищено `sync.RWMutex`, чтобы несколько запросов могли читать данные одновременно.

---

## Почему данные хранятся в памяти

Окно хранения — всего 5 минут. Эти данные временные, после истечения окна они больше не нужны.

Использование базы данных здесь дало бы лишние расходы:

- запись каждого события;
- удаление старых данных;
- дополнительные задержки при чтении;
- усложнение инфраструктуры.

Для этой задачи хранение в памяти проще и быстрее.

Компромисс: при рестарте сервиса статистика теряется. В рамках задачи это приемлемо, потому что сервис работает с коротким временным окном и не обязан хранить историю навсегда.

## Хранилище статистики

Главная структура хранения находится в `internal/storage`.

Используется кольцевой буфер из 300 бакетов:

```go
[300]Bucket
```

Один бакет хранит статистику за одну секунду.

```go
type Bucket struct {
    Timestamp int64
    Counts    map[string]int
}
```

Так как 5 минут — это 300 секунд, массив из 300 бакетов полностью покрывает нужное окно.

---

## Как работает кольцевой буфер

Для текущей секунды вычисляется индекс бакета:

```go
idx := now % config.WindowSeconds
```

Если в этом бакете лежат старые данные, он очищается и используется заново.

Пример:

```text
секунда 1   → бакет 1
секунда 2   → бакет 2
...
секунда 300 → бакет 300
секунда 301 → снова бакет 1
```

За счет этого:

- память не растет бесконечно;
- не нужно хранить каждое событие отдельно;
- не нужен отдельный процесс очистки;
- старые данные вытесняются автоматически.

---

## Потокобезопасность

К хранилищу одновременно обращаются разные части приложения:

- обработчики сообщений записывают новые поисковые запросы;
- HTTP API читает текущий топ;
- ручки стоп-листа читают и изменяют стоп-слова.

Поэтому хранилище защищено через `sync.RWMutex`.

```go
type RingBufferStorage struct {
    mu        sync.RWMutex
    buckets   [config.WindowSeconds]Bucket
    stopWords map[string]struct{}
}
```

Для записи используется `Lock()`.

Для чтения используется `RLock()`.

Это сделано потому, что чтений намного больше, чем записей. Несколько HTTP-запросов могут одновременно читать топ, но запись должна быть эксклюзивной.

---

## Добавление поискового запроса

Метод `Add()` делает следующее:

1. Нормализует строку запроса.
2. Отбрасывает пустые значения.
3. Проверяет стоп-лист.
4. Выбирает бакет текущей секунды.
5. Очищает бакет, если он устарел.
6. Проверяет лимит одинаковых запросов в секунду.
7. Увеличивает счетчик запроса.

Нормализация нужна, чтобы запросы вроде:

```text
"IPHONE"
" iphone "
"iphone"
```

считались как один запрос.

---

## Защита от накрутки

В проекте есть ограничение на количество одинаковых запросов за одну секунду:

```go
const MaxQueryPerSecond = 50
```

Если один и тот же запрос приходит слишком часто в рамках одной секунды, лишние события не учитываются.

```go
if bucket.Counts[query] >= config.MaxQueryPerSecond {
    return
}
```

Это защищает топ от простых аномальных всплесков, когда один и тот же запрос пытаются искусственно поднять вверх.

---

## Получение Top-N

Ручка:

```http
GET /top?n=10
```

Возвращает самые популярные запросы за последние 5 минут.

При вызове `Top()` хранилище:

1. проходит по 300 бакетам;
2. берет только актуальные бакеты;
3. суммирует счетчики запросов;
4. сортирует результат по убыванию;
5. возвращает первые `N` элементов.

Такой подход простой и дает всегда актуальный результат.

Компромисс: сортировка выполняется при каждом запросе `/top`. В промышленной версии можно было бы дополнительно хранить заранее подготовленный топ и обновлять его в фоне, но в рамках этого тестового задания я считаю это удовлетворительным.

## Стоп-лист

Реализовано управление стоп-словами без перезапуска сервиса.

Стоп-слова хранятся как множество:

```go
map[string]struct{}
```

Поддерживаются ручки:

```http
GET    /stop-words
POST   /stop-words
DELETE /stop-words/:word
```

Если поисковый запрос содержит стоп-слово, он не попадает в статистику.

---

## RabbitMQ

RabbitMQ используется как брокер сообщений.

Очередь:

```text
search_queries
```

Сообщение имеет такой формат:

```json
{
  "query": "iphone"
}
```

Структура в коде:

```go
type SearchEvent struct {
    Query string `json:"query"`
}
```

---

## Почему в сообщении только query

Для текущих требований нужен только текст поискового запроса.

Поля вроде `user_id`, `session_id`, `ip` или `timestamp` не используются в бизнес-логике.

Время события определяется в момент обработки сервисом, потому что статистика считается по последним 5 минутам относительно текущего времени сервиса.

---

## Consumer и канал jobs

Consumer читает сообщения из RabbitMQ и перекладывает их во внутренний канал задач:

```go
jobs := make(chan amqp091.Delivery, 50)
```

Consumer не занимается бизнес-логикой. Он только передает сообщения дальше.

Это разделяет получение сообщений из RabbitMQ и их обработку внутри приложения.

---

## Пул воркеров

В приложении запускается фиксированное количество воркеров.

Каждый обработчик:

1. ждет сообщение из канала `jobs`;
2. разбирает JSON;
3. передает событие в сервисный слой;
4. обновляет статистику;
5. подтверждает сообщение в RabbitMQ.

Такой подход ограничивает параллелизм и не дает приложению создавать неограниченное количество фоновых задач.

---

## Подтверждение сообщений

После успешной обработки сообщение подтверждается:

```go
msg.Ack(false)
```

Если сообщение не удалось разобрать, оно отклоняется:

```go
msg.Nack(false, false)
```

Если сервис упадет до подтверждения сообщения, RabbitMQ сможет вернуть его обратно в очередь.

---

## Ограничение выдачи сообщений RabbitMQ

Для защиты приложения от перегрузки используется:

```go
channel.Qos(50, 0, false)
```

Это значит, что RabbitMQ не будет отдавать больше 50 неподтвержденных сообщений одновременно.

Так появляется естественное обратное давление: если обработчики не успевают, брокер перестает отдавать новые сообщения сверх лимита.

---

## Корректное завершение приложения

В приложении реализовано корректное завершение по `SIGINT` и `SIGTERM`.

Схема:

```text
получен сигнал остановки
    ↓
вызывается cancel()
    ↓
consumer прекращает чтение
    ↓
закрывается канал jobs
    ↓
обработчики дочитывают оставшиеся сообщения
    ↓
HTTP-сервер завершает текущие запросы
    ↓
приложение останавливается
```

Для этого используются:

```go
context.WithCancel()
context.WithTimeout()
```

## Метрики

Добавлены базовые метрики в формате Prometheus.

Примеры пользовательских метрик:

```text
search_events_total
search_events_invalid_total
top_requests_total
stop_words_count
```

Что они показывают:

- `search_events_total` — сколько поисковых событий успешно обработано;
- `search_events_invalid_total` — сколько сообщений не удалось разобрать;
- `top_requests_total` — сколько раз вызывалась ручка `/top`;
- `stop_words_count` — текущее количество стоп-слов.

В ответе `/metrics` также есть стандартные метрики Go-приложения: память, сборщик мусора, количество потоков и другие служебные показатели.

## Локальный запуск

Создать файл `.env`:

```env
HTTP_ADDR=:8080
RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672/
RABBITMQ_QUEUE=search_queries
WORKERS_COUNT=4
```

Запуск:

```bash
docker compose up --build -d
```

Проверка контейнеров:

```bash
docker compose ps
```

Проверка логов:

```bash
docker logs rwb-app
docker logs rwb-producer
docker logs rwb-rabbitmq
```

Остановка:

```bash
docker compose down -v
```

## Вывод по нагрузочному тестированию

Сервис выдержал около 30 тысяч запросов в секунду на ручке `/top` при 500 параллельных клиентах без ошибок.

Для текущего задания это приемлемый компромисс: архитектура специально оптимизирована под большое количество чтений и короткое временное окно.

## Компромиссы

### Данные хранятся только в памяти

Плюсы:
- быстро;
- просто;
- хорошо подходит для окна в 5 минут.

Минусы:
- данные теряются при рестарте.

---

### Top-N считается при каждом запросе

Плюсы:
- результат всегда актуален;
- реализация проще.

Минусы:
- при очень высокой нагрузке сортировка на каждый запрос становится дороже.

Возможное улучшение: считать топ в фоне и отдавать уже готовый снимок.

---

### Одно хранилище защищено одним RWMutex

Плюсы:
- простая и надежная потокобезопасность;
- легко проверить и тестировать.

Минусы:
- при очень высокой параллельной нагрузке появляется ожидание на блокировке.

Возможные улучшения:
- разделить хранилище на несколько частей;
- хранить готовый снимок топа;
- обновлять агрегированный топ отдельным фоновым процессом.
